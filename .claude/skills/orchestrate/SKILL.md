# Orchestrating

`CLAUDE.md` says what the words mean — whose queue this is, one task one agent, that the dispatcher prices what its workers file, that agents in one tree keep off each other. Read those there; they hold all day, not only during a pass. **This file is only how to execute one, and deliberately does not restate them.** It replaced the `drain` skill on 2026-09-10 (coo#81): there is one mode, and the pass works the queue as it stood when it started — what the pass itself files lands in `backlog` and waits for triage.

You are the dispatcher. You do not work an item yourself down one long thread; you read the board, split it into lanes, spawn a worker per task, watch them, and verify and commit what comes back.

## 1. Take your slice of the board

The queue's order, Status and Priority live on the project, not in the issues, so one read gets them:

```bash
/home/ita/coo/tools/board list --tsv | awk -F'\t' '$4 == "WeatherBaseline"'
```

That is 1 GraphQL point for the whole board, in project order. `--tsv` is: position, item id, type, **repo**, issue number, Status, Priority, Worker, Due, title — the count line goes to stderr, so it does not reach the filter. Yours is what `CLAUDE.md` says is yours — normally exactly those rows, and never another repo's.

Then drop, in this order:

- `Worker: ita` — skip.
- `Blocked` — skip; name the blocker in your report. If it has since cleared, unblock it and work it.
- `Review` — skip; it is waiting on its named human. If no human is named, that is the bug: name one in the body and leave it there.
- `backlog` — skip. It is the shelf, not the queue; a triage pass promotes from it, an orchestration does not.

What survives is the pass, in project order. Read each survivor's body now (`gh api repos/theitush/WeatherBaseline/issues/$n -q .body` — REST; `gh issue view` is GraphQL), because the next step needs to know what files each one will touch.

## 2. Split it into lanes

Parallelism is the point of this skill, and it has two constraints: **the tree** and **the box**. A split that ignores either one ends the pass early — the first as a clobbered file, the second as a dead session.

### The tree

Two workers in one checkout are safe only when the files they will reach for are disjoint, so:

- Group the survivors by the paths their work will touch. Tasks whose paths are disjoint run **at the same time**, each in its own subagent. Tasks that share a path run **one after the other**, in project order, in one lane.
- Name the split in every brief: the paths that worker owns, and the paths it must not touch because another worker holds them.
- Where two tasks cannot be split by path and you still want both running, one of them gets `isolation: "worktree"`; its branch is merged when it reports — a merge, never a clobber.
- Run as many lanes as the split allows and no more than you can watch. Model per worker is the card's `Worker` column, and it goes on the spawn as `model:` **every time** — `opus` unless the card says otherwise. A spawn with no `model` runs at whatever default this machine happens to carry, and on 2026-09-18 an orchestrator asked which that was answered Fable, then Opus, and had checked neither (coo#94). Passing it is what makes the answer yours.

### The box

Lanes share one machine's RAM, and the kernel does not care whose work it kills. On 2026-09-15 four uncapped workers ran at once on this box, one python reached **20.3 GB** of its 24 GB, and the OOM killer took `init.scope` — the cgroup holding the whole Claude Code process tree — **four times**, killing every agent session on the machine twice over (inbar#253). ~9 GB was pushed to swap first, so the box was unusable long before anything died. Ita, that day: *"ORCHESTRATE SO DO THINGS SIMULTANEOUSLY IF THEY ACTUALLY FIT IN MEM"*. So:

- **You are not alone on the box.** Other orchestrators, in this repo and the other five, run passes on the same 14 cores and 24 GB, and a cap one of them has reserved is invisible to `free` until its job grows into it — so two passes can each "fit" and together not (coo#174). At pass start, before the plan, run:

  ```bash
  /home/ita/coo/tools/machine-budget
  ```

  It lists every live Claude session on the machine (the name is the `SendMessage` address) and which are mid-pass and on what, every live `systemd-run` scope with the RAM and CPU it has claimed and whose it is, and what is left: RAM is total less **~4 GB** less every other scope's `MemoryMax` counted in full, and cores are `nproc` less one less what is claimed or busy. **Say hello** to each session it shows mid-pass — one `SendMessage` line: your repo, your lanes, the RAM and cores you are about to claim. Ita, 2026-09-23: *"when starting they shuold see whos running and say hello"*.
- **Budget the box before you spawn.** The pass's budget is what `machine-budget` says is left — not `free`, which counts only what the others use this second. The sum of the lanes' RAM caps may not exceed it, and neither may the sum of their CPU (`-p CPUQuota=<cores×100>%`, and `-j<cores>` for a build or a test runner that fans out).
- **Re-check before every heavy launch**, not only at pass start: `/home/ita/coo/tools/machine-budget --left` prints `<GB> <cores>` in half a second, and another pass may have claimed half the box since you planned. If what you are about to start no longer fits, it waits behind whatever is running, rather than squeezing in under a smaller cap.
- **Every heavy job runs capped, in its own cgroup, and never in swap.** Heavy is anything whose footprint you cannot bound by eye — a backtest, a training run, a dataset read, a build, a full test suite, any ad-hoc script over a large file:

  ```bash
  systemd-run --user --scope -q -p MemoryMax=<N>G -p MemorySwapMax=0 -p CPUQuota=<C×100>% -- <command>
  ```

  `MemorySwapMax=0` matters as much as the cap: without it the job thrashes the whole machine before its own cgroup reclaims. A capped job that overruns dies with 137 and takes **only itself**; an uncapped one takes every session on the box. (Verified on this box 2026-09-15: a 600 MB allocation under `MemoryMax=256M` was killed, the shell that launched it untouched.)
- **Size the cap from a measured peak, not an estimate.** Peaks live in the repo's own memory or an issue's result; where none is recorded, cap it at what you can afford and *measure it this run* — `/usr/bin/time -v <command>` prints `Maximum resident set size`, and the number goes into the result so the next dispatcher sizes from a fact.
- **Run everything that fits, and no more.** Lanes whose caps fit the budget together run at once; the rest queue behind them, in project order. Narrowing a pass below what the box can hold wastes the machine — the point is simultaneous, not serial.
- **A worker that hits its cap reports the number and never raises it.** A job needing more than its documented peak is news: it goes in the report and in the issue, and the dispatcher decides whether the pass still fits.

Write the plan down before spawning anything — one line per task, the ones you skipped included:

```bash
/home/ita/coo/tools/orchestrate-status plan <<'EOF'
WeatherBaseline#74 | CLEANUP: retire queue.json            | 2 | 20
WeatherBaseline#75 | RUN: re-measure board cost            | 2 | 20
WeatherBaseline#76 | BUG: sign drops the surname           | skip |  | Blocked on inbar#40
EOF
```

The columns are id, title, lane, your estimate in whole minutes, and a note; `skip` in the lane column is a task you saw and passed over, and the note is why. A skipped row is recorded and **never rendered** (§4) — the panel is what is happening, not what is not — so the file stays a true record of the pass while `Planned` holds only what is going to run next; what you passed over is prose in §6's report. That file *is* the pass — it is what the panel renders, before, during and after the pass, so it is also what a reader compares the finished pass against. Re-run `plan` whenever the shape of the pass changes (a task added, a lane re-cut, an estimate you now know better): it re-orders and re-estimates, and it never un-runs anything that has already started or landed. The first `plan` of a new pass is no different: it keeps every Done row the conversation already has, so Done is everything landed since the conversation began, not since this pass did (§4).

## 3. Spawn, watch, land

For each task, in this order:

```bash
n=<n>
/home/ita/coo/tools/board set WeatherBaseline $n Status "In Progress"        # before the spawn, so a crash leaves evidence
/home/ita/coo/tools/orchestrate-status start WeatherBaseline#$n --eta 20     # stamps the real start; the panel counts down from it
```

Then spawn its worker into this repo with `model:` set to the card's `Worker` — passed explicitly, never left to inherit — with the issue body as context and this brief:

> You hold `WeatherBaseline#n` and nothing else. Sign it (`/home/ita/coo/tools/sign WeatherBaseline n <YourName>`) before the work. His ask is in the issue body's **Ask** block, in his own words — read it there. Nothing in this brief restates it, and any reading of it here is mine, not his. You own these paths: `…`; do not touch `…`, another worker holds them. Your budget is **`<N>` GB and `<C>` cores**, and other sessions share this box: run anything heavy under `systemd-run --user --scope -q -p MemoryMax=<N>G -p MemorySwapMax=0 -p CPUQuota=<C×100>% -- …` (and `-j<C>` where the tool fans out), never uncapped and never into swap, check `/home/ita/coo/tools/machine-budget --left` first and wait if it no longer fits — and say so on my panel as you start waiting, `/home/ita/coo/tools/orchestrate-status eta WeatherBaseline#n <minutes left> --why wait --note "machine-budget"`, and report its peak (`/usr/bin/time -v`, `Maximum resident set size`) — if you hit the cap, report the number rather than raising it. Your row on my panel counts down from an estimate I made from outside; you are the one who knows when it is off, so say so the moment it is: `/home/ita/coo/tools/orchestrate-status eta WeatherBaseline#n <minutes left> --why wait|load|scope|blocked --note "<what>"` — `wait` when you are waiting on something outside the task (a budget slot, a lock, another task), `load` when the box is slow, `scope` when the work is bigger or smaller than it looked, `blocked` when you cannot go on — and `--why ready` with a fresh estimate once a wait is over. Do the work, verify it (tests, build, a read of the diff — the result is a claim you are signing), file whatever the work did not reach as its own issue at `Status backlog` before this one closes, and finish it exactly one of three ways per `CLAUDE.md`: **Done** (result block below a `---` rule, close the issue, `Status Done`), **Review** (issue stays open, one-line `**Review:** <who> — <what> — <where>` as the body's first line, `Status Review`, commit says `Refs #n`), or **Blocked** (blocker in the body, issue open, `Status Blocked`). Report back: what you did, how you verified, where it landed, which issues you filed, and the exact paths you left uncommitted.

**The brief never re-types his words.** The ask lives once, in the issue body's `**Ask**` block, and the worker reads it there — a brief that quotes it makes a second copy that can drift, and on 2026-09-18 it did: `countrous` came out `contours`, `diagnoal` came out `diagoanl`, and two of fourteen rounds went on undoing the reading the tidied word licensed (coo#93 §2). Where a task needs *your* reading of an ambiguous ask, write it outside the blockquote and say it is yours. And if the ask has a question in it, ask him before you spawn — not after the worker builds.

**Name the task in the spawn's `description`** — `WeatherBaseline#n` somewhere in it, which `Work WeatherBaseline#74 …` already does. That is the whole of what a clickable row needs: the panel finds a worker's transcript by matching that description, so `start` takes nothing extra and a pass written the usual way links itself (§4). Where the match cannot be made — a worker spawned before its row existed, a task you worked by hand — say where the row points instead, with `/home/ita/coo/tools/orchestrate-status start WeatherBaseline#$n --agent <id>` or `--link <path|url>`. A **planned** task points at the brief you are going to send it, once you have written it down:

```bash
/home/ita/coo/tools/orchestrate-status brief WeatherBaseline#$n <<'EOF'
You hold WeatherBaseline#$n and nothing else. …
EOF
```

That is optional, and it is the one way to read a brief before it is sent: nothing can put unsent text into a running session's prompt box, so the brief is a file the planned row links to, editable up until the spawn (coo#102).

**Pause the clock before you stop, and resume it after.** A pass that stops mid-flight — the laptop going to sleep, Ita calling a halt, a wait on him that holds every lane — runs `/home/ita/coo/tools/orchestrate-status pause` first and `/home/ita/coo/tools/orchestrate-status resume` when it picks up again; with no id each covers every Running row, with ids only those. A paused row's ELAPSED stops, its countdown holds, and the span comes off the `(+5m)`, the `**Timing:**` line and the board's `Actual` that `land` writes (Ita, 2026-09-23, coo#170: *"stop the timer when a task is paused"*). A stop nobody announced is corrected afterwards: `pause WeatherBaseline#$n --at <from> --until <to>` records the span that already happened.

**The worker re-estimates its own row; the brief tells it to.** Your `--eta` is a guess from outside; the worker knows when it is sitting behind a `machine-budget` slot or a suite crawling on a loaded box. So the brief (below) has it run `/home/ita/coo/tools/orchestrate-status eta WeatherBaseline#n <minutes left> --why wait|load|scope|blocked|ready --note "…"` — `+N` adds to what is left — and the row's countdown re-bases from now, the lane behind it moving with it. The revision never touches the row's `eta`, so the `(+5m)` still measures your estimate; what it adds is *why*: the Done row reads `Done · wait +15m`, and the `**Timing:**` line `land` writes lists every revision with its time, reason and note, so a later look can tell a task that was late because the box was busy from one that was estimated wrong (Ita, 2026-09-23, coo#178: *"they do know when they are just waiting for a slot to free up"*). A worker with no pass behind it is told so and nothing fails. **The clock reminds it, too:** a PostToolUse hook (`/home/ita/coo/tools/eta-ping`, installed by `orchestrate-status install`) puts a one-line note in the worker's context with its next tool result, once at 5 minutes left and once at 0, and a fresh `eta` re-arms both (Ita, 2026-09-23, coo#193: *"like at 5min and again at 0min"*). It finds the worker by the `description` §3 has you spawn it with, or by `start --agent`, so a worker spawned under some other description hears nothing. A worker that goes quiet past its estimate is not re-estimated for it — ask it.

When a worker reports, before starting anything else in its lane:

1. Read its result against the issue — you are the one who verifies before anything reads Done; what you cannot verify by looking goes to `Review` with what and who in the body.
2. Stamp the finish, which measures the duration for you:

   ```bash
   /home/ita/coo/tools/orchestrate-status land WeatherBaseline#$n Done
   /home/ita/coo/tools/orchestrate-status land WeatherBaseline#$n Review  --note ita
   /home/ita/coo/tools/orchestrate-status land WeatherBaseline#$n Blocked --note "inbar#40"
   ```

   Exactly the three ways a task is allowed to finish. `--at HH:MM` is for when you notice a few minutes late; without it the clock is now. `land` also writes the timing to the task itself — its `--eta` and the measured span into the board's `Estimate` and `Actual` columns (minutes), and one `**Timing:** est ~20m · took 25:00 (+5m) · 124.8k tokens` line into the issue body, replaced on a re-land — so estimates can be tuned later against what tasks really took (coo#163). It never fails `land`; a board write the budget refuses is queued for `tools/board flush`.
3. Commit **by path** the paths its report names, and nothing else. Never `-A`: the tree is shared.
4. Start the next task in that lane.
5. Send a message saying what landed and what you started behind it — a line or two, no footer. The panel at the bottom of the terminal is carrying the lists, live and recomputed, and it is the only place they go (§4).

## 4. The panel

The three lists — what is running, what is planned, what is done — are one file now, written by the commands in §2 and §3 and rendered in two places.

**The panel** is the status line: Claude Code re-runs it on every assistant message and pins each line of its output to the bottom of the terminal. So the headings sit in one place and stop scrolling away, which is what Ita asked for (coo#87): *"i just want to have the running, ran, planned in a fixed format that doesnt go anywhere instead of the text written at the end of every msg."* There is nothing to set up per pass — `plan` brings the panel up, and a session that has never run a pass shows no headings at all. **A finished pass stays on it**: after the final report the Done rows are still pinned, until Ita dismisses them (Ita, 2026-09-22, coo#137: *"can you add a task so that it stays? like even when youre done coz now id wanna see it also at the bottom and not as part of your prompt"*). **Done accumulates for the conversation**: the next pass's `plan` puts its own rows above the last pass's Done rows rather than replacing them, and only `clear`, or `/clear` starting a new conversation, empties Done (Ita, 2026-09-22, coo#142: *"also the done tasks should still be in the done list until the session is cleared"*). `/home/ita/coo/tools/orchestrate-status clear` is the dismiss — his to run from the prompt, or yours when he asks; the skill never runs it.

**It is one table across two panels.** Claude Code's own subagent panel draws a row for every live worker, and since coo#104 each of those rows *is* its pass row; the pinned panel carries the rest — Planned and Done — and leaves off every row the subagent panel is drawing, so nothing is on screen twice (Ita, 2026-09-22, coo#135: *"if the subagents thing insists on showing only running tasks, we can just show the planned and done under it?"*). The subagent panel records which rows it drew on each tick, beside the pass file; the pinned panel reads that record and hides those rows and no others. So a Running row whose worker has no line up there — not spawned yet, evicted 30 seconds after it ended while you have not landed it, spawned by another session — stays on the pinned panel, and a record more than 15 seconds old is ignored, so a subagent panel that has stopped drawing hands every row back. A stage whose rows are all up there is left out rather than printed as `—`. `/home/ita/coo/tools/orchestrate-status show` prints the table whole and plain on stdout, never split.

**The bottom of the table rides under the last worker.** Claude Code draws the status line *above* the prompt's hint line and its subagent panel *below* it, in fixed code with no setting to swap them, so two panels read as one table upside down — Planned and Done over Running (Ita, 2026-09-22, coo#138: *"its showing the subagents at the bottom and the planned and done at the top"*). So while any worker has a row down there, Planned and Done are packed as extra lines into the **last** of those rows (the one started latest — the panel orders by start time), and the pinned panel keeps only any Running row with no worker line. Top to bottom it then reads Running, Planned, Done. Those extra lines belong to that worker's row, so clicking one opens that worker — the row is one click target, and nothing its content carries changes that (coo#143). They sit under a thin dim rule, and they are drawn in colours of their own and **bold all the time**, so neither selecting the row nor opening it changes them: Claude Code bolds the row it has open and nothing in a row's content can take bold off, so the tail has it already and only the worker's own line changes (Ita, 2026-09-23, coo#143: *"im sure there is a more creative solution no? like put a line there"*). A decorated row is only our text, so it loses Claude Code's own per-second elapsed and token count, and its ELAPSED steps every 5 seconds, when the hook is re-run (coo#156); with no worker listed, the record goes stale within 15 seconds and the whole table is back on the pinned panel. The subagent panel's own `● main` row is drawn by Claude Code itself — a fixed word, no count, not in what the hook is handed — so it cannot read "orchestrator". **The token counts are Giverny's, on its model line**: `Opus 5.5  ·  5h 55%  ·  wk 60%  ·  session 115.4k  ·  total: 774.7k`, the session's own count and it plus every subagent's, printed by `giverny statusline` itself and always, pass or no pass (giverny#22; Ita, 2026-09-23, coo#177: *"im saying i want that tokens thing as part of giverny not coo!"*). The wrapper adds no count of its own there, and the table has no total row. All it appends, at render time and without ever writing Giverny's config, is a usage limit the pass is stalled on: `…  ·  5h limit → 15:20`, a line of its own when nothing is printed above. So the pinned panel has no `Session` row. `show` still prints the orchestrator as the table's top row, having no model line to lean on.

**In a Giverny tab with its agents pane on, the table moves into the pane.** The subagent-panel hook hands each tick, unchanged, to `giverny relay --subagent-line`; with the pane on that hides every row of Claude Code's panel, `● main` with them, and the pane draws the workers from Claude Code and Planned, Done and the ETAs from the feed `/home/ita/coo/tools/orchestrate-status` writes — so the pinned panel draws none of the table either, and the pane is where you watch the pass. With the pane off, outside Giverny, or with a Giverny build too old for the flag, both panels are exactly as above (coo#169).

It is a table — the orchestrator's own row at the top (in `show` only; on the panel the count is Giverny's model line), then Running, then Planned, then Done, the stage written on every row — in the columns STAGE, TASK, ELAPSED, ETA, NOW and TOKENS, every one but TASK a fixed width and TASK taking the rest of the terminal, so nothing jumps between renders (Ita, 2026-09-17, coo#90: *"running then planned then ran … stage, task, eta in fixed length columns"*). **There is no header row** — the columns stand on alignment (Ita, 2026-09-23, coo#149: *"no need for the headers of stage/tst/elapsed/etc"*). The count is the last column, so the eye scans a straight edge down the right of the table (Ita, 2026-09-19, coo#117: *"the tokens should be the most right column"*). Claude Code runs the status line with `COLUMNS` and `LINES` set to the terminal's size, so the panel sizes itself to the window; `/home/ita/coo/tools/orchestrate-status width <cols>` is only the fallback for a status line run some other way, and unset it lays out for 120. Every render comes from the same file, so the pinned panel, the subagent panel and `show` cannot disagree, and what the renderer guarantees you no longer have to:

- **Every line names the task by id *and* title.** A title longer than the column is cut with an ellipsis; the id never is.
- **Three clock columns, each one kind of thing.** **ELAPSED** is how long a row has been going, or took; **ETA** is how much longer until it is finished; **NOW** is what a Running row's worker is doing this minute, or where a Done row landed (Ita, 2026-09-23, coo#149/coo#150: *"add an elapsed time also next to the eta.. so the done ones just show the elapsed time"*, and *"add another col for whatever the agent is doing now in the task? … it can actually be the thing in the done/review col and the elapsed can go to its left"*). So a Running row fills all three and a Planned row has only its ETA. **A Done row's ETA is how it came out against its estimate** — `(+5m)` late, `(-1h20m)` early, `(±0m)` on the minute, blank when it was started with no `--eta` (Ita, 2026-09-23, coo#160: *"on the done tasks, on the eta col (which they have empty) something like (+5m) or (-1h20m) where + is late and - is early"*). It is ELAPSED minus the estimate in whole minutes, measured and so without a tilde, and a usage-limit stall the row sat through counts as late: it is wall time the task really took.
- **Durations read `~5m`, `~1h3m`, `~1d3h12m`** (Ita, 2026-09-23, coo#145: *"like ~5m or ~1h3m or ~1d3h12m with the tildas"*), units that are zero left out — `~1h`, not `~1h0m`; the tilde says it is an estimate. A row past its estimate keeps a leading minus, `-~12m`, a countdown through zero. **ELAPSED is a stopwatch instead** — `0:42`, `14:05`, `1:03:07`, only the digits it needs (Ita, 2026-09-23: *"elapsed should be hh:mm:ss but only what the digits are necessary ofc"*) — measured, so no tilde, and `start`/`land` stamp to the second for it. Both columns are right-aligned. The finish clock, the `since 14:20` and the `lane 2 after #74` note that once shared the ETA column are long gone: the lanes are still chained exactly as they were, and which lane a task is in is §2's business and the report's.
- **NOW on a Running row is the worker's own activity.** On Claude Code's subagent panel it is the line Claude Code itself would show for that worker — its progress summary, handed to the hook as `tasks[].label` — and everywhere else, or before the CLI has a summary, it is the last tool call or line of text in the worker's transcript (`Reading board.html`, a Bash call's description). Cut to its column; the id and the numbers never move.
- **Clocks survive midnight.** `start` and `land` write the full date and time (`2026-09-23T00:12:07`), and a bare `HH:MM` in a file written before that is read as the latest such time at or before now, so a row started at 23:48 reads `14:00` gone at 00:02, not a day (coo#144).
- **Done** is every task finished so far this conversation — this pass and every pass before it since the last `clear` (coo#142) — the span it took, and where it landed — **newest first**, so the last thing to land is the top Done row (Ita, 2026-09-19, coo#117: *"the last done should be at the top"*). A Review line names its reviewer; a Blocked line names its blocker, in NOW. **The stage means this pass is done with the task, not that the board says `Done`** — a `Done` row can read `Review — ita` or `Blocked on inbar#40` in NOW, because that is where it landed and the stage is only that the pass let go of it. It was called `Ran` until 2026-09-19 (Ita, coo#110: *"ran in green and it should be called done"*); the plan file still writes the state as `ran`, which nothing but the renderer reads.
- **Running** counts itself down. `~20m` is `start + eta − now`, recomputed every time the panel re-renders, so it is true between your messages as well as in them — and a worker past its estimate goes to `-~12m` instead of sitting at "20m left" forever. **A usage limit brings its own wait with it:** once one is actually hit, every Running and Planned row grows by the time until that limit resets — `~20m` reads `~1h20m` the moment a five-hour limit goes at an hour to the reset, shrinks as the reset comes round and is back to `~20m` when it lands — because nothing is running in between, and a panel counting two workers killed by the session limit down to `-02:30` for two hours is what Ita saw on 2026-09-22 (coo#130: *"the eta timer needs to adjust to the token limits"*). Until a limit is hit it changes nothing, and the end of the model line names the one that is out.
- **A re-estimated row counts down from the worker's figure.** After `eta` (§3) the countdown is what the worker said was left, from when it said it; while its latest reason is `wait` or `blocked` NOW reads that reason and note instead of its activity (`wait: machine-budget …`) (coo#178).
- **A paused row's clock stands still.** Between `pause` and `resume` (§3) its ELAPSED does not move, its countdown holds and the lane behind it waits with it, and NOW reads `paused since 12:58`; the span never counts as time the task took (coo#170).
- **Planned** rows are chained down each lane from whatever is running in it, so a worker landing early or late moves every line behind it. That is the whole-chain recalibration this section used to ask you to do by hand, and it is the part that was always wrong when you did. The chain is not written on the row — only its result, the time left.
- **`Planned` is only what is going to run next, and there are only these three stages.** A task you saw and passed over — `Worker: ita`, `Blocked`, `Review`, `backlog` — is kept in the file by `plan` and appears on the panel **nowhere**: not on Planned, and not in a stage of its own. Ita, 2026-09-19 (coo#97): *"planned is ONLY things that are planned to go next in line"*, and, on being shown a `Skipped` stage built for the rest: *"lol ffs skipped is not in the fucking spec. why am i seeing skipped things"*. The panel is the room you have for what is happening; §6's report is where you name what you passed over, in prose, with the reason.
- **Every `Running` and `Done` row carries the tokens its worker has used**, re-read from that worker's transcript on every render, so a running row's count climbs while it works (Ita, 2026-09-19, coo#103: *"i want a token count on the tasks also. updated like in the subagents thing"*). It is the number Claude Code's own agents view shows beside a subagent — **the context that agent is carrying right now, plus every output token it has written** — so the panel and that view agree; it is not what the agent has been billed, which counts the same context once per turn. A `Planned` row has no worker yet and a row whose worker cannot be found prints nothing, never an error, and the column is a fixed width, rightmost since coo#117, so a count going from `9.9k` to `124.8k` moves nothing.
- **One row of the table is not a task.** The orchestrator's own count is a row at the **top** of `show`, shaped like any session's — a stage, a title, a count, no ETA — there only when there is something to count, holding no task and not tinted: the colour says what a *task* is doing. On the pinned panel it is not drawn, since Giverny's model line carries `session <count>  ·  total: <count>` (coo#177). The ledger `total:` row that ended the table from coo#117 went with it: the total is Giverny's now, and a second copy of it would only disagree.
- **A row's id is a link.** `Running` and `Done` link to their worker's transcript, `Planned` to the brief `brief` wrote for it — an OSC 8 hyperlink on the id alone, so ctrl+click on `WeatherBaseline#74` opens what that row is about (Ita, 2026-09-19, coo#102: *"i want to be able to click on the agents running or does that ran and it would take me to them"*). What follows the URL is the terminal, not Claude Code, so the link itself still reaches no view inside it — but since coo#104 the pass's rows are *in* Claude Code's own subagent panel, the one under the prompt and at `/tasks`: each running worker's row there is rendered as that worker's pass row, the same id, title, time left, tokens and colour, and those rows open natively — a plain click anywhere on the row, or Enter on the selected one, with no modifier and no file (Ita, 2026-09-19, coo#104: *"clicking … should be on all the row and it should be WITHOUT CTRL and it should open claude code in there like the subagents thing does. now it just opens a jsonl file"*). Only a **running** worker has a row there, and nothing can add one: that list is Claude Code's own live subagents, and a line whose id is not one of them is thrown away, so Planned, Done and the orchestrator's row get no row of their own there — they ride as extra lines under the last worker's row while there is one, and the pinned panel stays, carrying the rest whenever nothing is running, with Giverny's token counts on the model line above it (coo#129 read this out of the CLI itself, 2.1.278, and filed coo#132 to ask Anthropic for the rest; coo#138 re-read it for 2.1.280). A worker that lands keeps its row for exactly 30 seconds — a hard constant with no setting behind it — and is then evicted along with its transcript, and once it is gone nothing reopens it, so the link on a `Done` row's id is still how you get back into a worker that has finished. Inside those 30 seconds, though, **opening the row keeps it**: click it or press Enter on it and Claude Code holds it for as long as the view stays open, leaving the view starts a fresh 30 seconds, and `x` on a selected finished row clears it at once. While a row is in that window its tail says what became of its worker — `7:00` and `worker done`, or `worker failed` / `worker killed` — instead of a countdown that would go on falling past zero on a worker that has already exited; that is the one thing the two panels do not agree on, because only Claude Code's is told. The URL is invisible on screen, so `/home/ita/coo/tools/orchestrate-status links` prints what every row resolves to and what the environment makes of it; `ORCHESTRATE_LINKS=0` turns the escapes off; and where Claude Code does not detect a hyperlink-capable terminal the id just prints as text, which is why `FORCE_HYPERLINK=1` in its environment is worth having. - **Each stage has a colour** in the terminal: `Running` a mid blue, `Planned` a steel blue-grey, `Done` green (Ita, 2026-09-19, coo#110: *"maybe diff colors? like blue for running and slightly beigher for planned and ran in green"*, and then *"i dont like this beige… i said light blue.. so keep the current blue for running and make it ligher blue for what is currently beige"*). - **The panel is capped** at half the terminal, and Done collapses from the oldest into a `+N earlier` count — which, now that the newest is at the top, is the bottom of that stage; a status line cannot scroll. `/home/ita/coo/tools/orchestrate-status expand` lifts the cap for this session and `collapse` restores it — Ita runs them from the prompt as `! …/orchestrate-status expand`, and so can you when he asks. - Times are measured, never guessed: `start` and `land` stamp the clock themselves. ELAPSED was timed, to the second; ETA is the `--eta` you gave, counted down, and its `~` says so (coo#145). Once the first worker lands, re-run `plan` to re-estimate the rest against what it actually took.

**The file is per conversation, not per repo**, because the panel has to be true of the terminal it is pinned to — two sessions open in the same repo (Ita's and yours) would otherwise overwrite each other's pass.
